Rust, Swift and Dart are generated by *sidekick*, the template engine that
lives inside the Librarian binary. Adding a fourth language means writing a
new codec package and then registering it in a handful of switches that key
on the language name. None of those switches has a default that does the
right thing, so a language that is missing from one of them fails at run
time with an error such as `language "kotlin" does not support cleaning`.

This walkthrough is the checklist. It assumes you know how a generation
runs; if not, read
[Inside generate: how sidekick produces code](generate-and-sidekick.html)
first. Two existing languages are used throughout:

- **Dart** (`internal/sidekick/dart`, `internal/librarian/dart`) is the
  smallest complete implementation and the easiest to copy for the glue
  code in `internal/librarian`.
- **Swift** (`internal/sidekick/swift`) is what `internal/sidekick/AGENTS.md`
  calls the architectural reference for the codec itself: one file per
  annotated node type, small helpers with 1:1 tests, typed configuration.

Placeholders below use `<lang>` for the lowercase name used in
`librarian.yaml` and Go package paths, and `<Lang>` for the Go identifier.

## What you get for free and what you write
<!-- step runs="Librarian repository" code="librarian" -->

The parser and the model are shared. Every sidekick language receives the
same `*api.API` from `parser.CreateModel`, already cross-referenced,
validated and trimmed by `included_ids`/`skipped_ids`. The language-specific
part is three things:

1. A **codec package** under `internal/sidekick/<lang>` that annotates the
   model and renders embedded Go templates.
2. **Configuration types** under `internal/config` that describe what a
   library of that language can set in `librarian.yaml`.
3. A **glue package** under `internal/librarian/<lang>` that turns a
   `config.Library` into a `parser.ModelConfig`, calls the codec, and runs
   the ecosystem formatter.

```flow
title: Where the new code goes
lanes:
  - id: core
    label: librarian core (switches on language)
    kind: lib
  - id: glue
    label: internal/librarian/<lang>
    kind: lang
  - id: shared
    label: shared engine (parser, api, language)
    kind: lib
  - id: codec
    label: internal/sidekick/<lang>
    kind: lang
nodes:
  - id: dispatch
    lane: core
    label: generateLibraries / cleanLibraries
    step: 7
  - id: model
    lane: glue
    label: libraryToModelConfig
    step: 4
  - id: parse
    lane: shared
    label: parser.CreateModel
  - id: annotate
    lane: codec
    label: annotateModel
    step: 5
  - id: render
    lane: shared
    label: Templates.GenerateFromModel
    step: 6
  - id: format
    lane: glue
    label: Format
    step: 7
edges:
  - dispatch -> model
  - model -> parse | ModelConfig
  - parse -> annotate | *api.API
  - annotate -> render | embedded .gotmpl
  - render -> format | files under Output
```

The purple lanes are what you write. For Dart, the whole glue package's
generate path is eighteen lines:

```excerpt
file: internal/librarian/dart/generate.go
start: "func Generate(ctx context.Context, cfg *config.Config, library *config.Library, sources *sources.Sources) error {"
end: "+17"
caption: Build a ModelConfig, parse, hand the model to the codec. Everything else is shared.
```

## The configuration types
<!-- step runs="Librarian repository" code="librarian" -->

Four edits in `internal/config`, all mechanical:

1. Add `Language<Lang> = "<lang>"` to the constant block in
   `internal/config/language.go`. Every switch in the rest of the tree
   compares against this constant, and `librarian.yaml`'s `language:` field
   must equal it.

```excerpt
file: internal/config/language.go
start: "// LanguageRuby is the language identifier for Ruby."
end: "+6"
caption: The language constants. There is no registry; the string is the identity.
```

2. Create `internal/config/<lang>.go` with pure-data structs. Swift uses
   `SwiftDefault`, `SwiftPackage`, `SwiftModule` and `SwiftDependency` in
   `internal/config/swift.go`; Dart uses a single `DartPackage` for both the
   default and the per-library block (in `internal/config/language.go`). The
   structs carry `yaml:"...,omitempty"` tags and doc comments; keep them free
   of methods and logic, because `tidy` round-trips them through YAML.

3. Add one pointer field to `Default` and one to `Library` in
   `internal/config/config.go`, tagged with the language name.

```excerpt
file: internal/config/config.go
start: "// Dart contains Dart-specific library configuration."
end: "+25"
caption: The per-library language blocks. Default has the same shape a few lines above.
```

4. Regenerate `doc/config-schema.md`. It is produced from the struct
   comments by the `go:generate` directive at the top of `config.go`, so a
   new struct without regeneration leaves the documentation stale.

```excerpt
file: internal/config/config.go
start: "//go:generate go run -tags configdocgen"
end: "+1"
caption: Run go generate ./internal/config after adding or changing fields.
```

## Defaults and preview merging
<!-- step runs="Librarian repository" code="librarian" -->

`applyDefaults` runs once per library per command and does two things that
each need a per-language function in `internal/librarian/library.go`.

`fillDefaults` copies repository-wide values from `default.<lang>` into a
library that did not set them. It dispatches on which `Default` field is
non-nil, so your case must be added to the switch and backed by a
`fill<Lang>`:

```excerpt
file: internal/librarian/library.go
start: "func fillDefaults("
end: "+28"
highlight: "case d.Dart != nil:"
caption: fillDart (further down the file) is a dozen lines of "if empty, copy from default".
```

`resolvePreview` builds the `-preview` variant of a library by overlaying
`library.preview` on the stable entry. The common fields are handled
generically; the language block needs a `merge<Lang>` that merges every
field, because a field forgotten here is silently dropped from preview
libraries:

```excerpt
file: internal/librarian/library.go
start: "if p.SpecificationFormat != \"\" {"
end: "+22"
highlight: "switch language {"
caption: Both the switch case and the merge function are yours to add.
```

Two optional hooks in the same file matter only if your language has
multi-module "veneer" libraries or library names that cannot be turned back
into an API path: `isMixedLibrary` and `canDeriveAPIPath`. Dart needs
neither.

## The Library to ModelConfig builder
<!-- step runs="Librarian repository" code="librarian" -->

`parser.ModelConfig` is the contract between Librarian's configuration and
the shared parser. Each language has a small function that fills it; Dart's
`toModelConfig` in `internal/librarian/dart/codec.go` is the one to copy.
It does three things in order:

```excerpt
file: internal/librarian/dart/codec.go
start: "func toModelConfig("
end: "+18"
caption: Reject unsupported formats, build the source roots, look up the service config.
```

- `sources.NewSourceConfig(srcs, library.Roots)` resolves `library.roots`
  (default `googleapis`) to directories on disk and carries an optional
  `IncludeList` to restrict which `.proto` files are compiled.
- `serviceconfig.Find(root, path, language)` consults the embedded
  `sdk.yaml` and then scans `<googleapis>/<path>/*.yaml` for a
  `type: google.api.Service` document. The language argument lets `sdk.yaml`
  carry per-language release levels and transports.
- Showcase is special-cased because its protos do not live in `googleapis`.

The result is assembled into the `ModelConfig`:

```excerpt
file: internal/librarian/dart/codec.go
start: "modelConfig := &parser.ModelConfig{"
end: "+15"
caption: SpecificationFormat, SpecificationSource, ServiceConfig, Source and Protoc are what the parser needs; Codec and Override are yours.
```

`Override` carries the name, title, description and skipped IDs that the
shared post-parse passes apply to the model. `Codec` is a `map[string]string`
in Dart and Rust; Swift and `codec_sample` skip the map and pass the typed
`*config.Library` straight to the codec, which is the pattern the skill
recommends for new languages (the next step shows why). Dart only supports
`protobuf`; Rust's `libraryToModelConfig` in `internal/librarian/rust/codec.go`
shows the extra `switch` needed to pick a Discovery or OpenAPI source from
`sdk.yaml`.

The same package should also export `Format`, `DefaultOutput`,
`DefaultLibraryName` and, if the name/path mapping is not simply
`-`/`/`, `DeriveAPIPath`. All of them are a few lines in
`internal/librarian/dart/generate.go`.

## The sidekick codec package
<!-- step runs="Librarian repository" code="librarian" -->

Start from `internal/sidekick/codec_sample`, which is a complete, tested
codec that emits a single README. Its entry point is the whole pipeline in
miniature:

```excerpt
file: internal/sidekick/codec_sample/generate.go
start: "func Generate(_ context.Context, model *api.API, outdir string, cfg *config.Library) error {"
end: "+7"
caption: Construct the codec from typed config, annotate, pick output files, render.
```

There is no Go interface a codec must satisfy. `internal/sidekick/language`
provides helpers (`GeneratedFile`, `WalkTemplatesDir`, `PathParams`,
`QueryParams`, `FilterSlice`, ...), but what makes something a codec is that
it fills the `Codec any` field on each model node (`api.API.Codec`,
`Message.Codec`, `Method.Codec`, and so on) with a struct the templates can
read. The driver that does this is `annotate_model.go`:

```excerpt
file: internal/sidekick/codec_sample/annotate_model.go
start: "func (c *codec) annotateModel(model *api.API) error {"
end: "+21"
caption: Model annotations carry CopyrightYear and the license boilerplate; then one pass per node kind.
```

The layout rules from `internal/sidekick/AGENTS.md`, which `codec_sample`
already follows:

| File | Holds |
|---|---|
| `codec.go` | `codec` struct and `newCodec`; nothing else |
| `annotate_model.go` | The only traversal driver. Messages and enums before services. |
| `annotate_<node>.go` | One file per node kind: `service`, `method`, `message`, `field`, `oneof`, `enum`, `enum_value`; each with a `_test.go` |
| helper files | Naming, doc formatting, path formatting as small files with 1:1 tests (see `names.go`, `format_path.go`, `doc_link.go` in Swift) |
| `generate.go` | `//go:embed all:templates`, `Generate`, output-file selection |

Swift (`internal/sidekick/swift`) is the full-size version of this layout:
ten `annotate_*.go` files plus about fifteen helper files, each with a test.
Rust and Dart predate the rules; Dart keeps everything in one
`annotate.go` and Rust has a 1,700-line `codec.go`. Do not copy those
shapes.

The one hard constraint comes from the template engine: templates cannot
compute, so any string the output needs (a type name, a doc comment, a
URL-safe path, a sorted list) must already be a field or a zero-argument
method on an annotation struct.

## Templates
<!-- step runs="Librarian repository" code="librarian" -->

Templates are Go `text/template` files with the `.gotmpl` extension under
`internal/sidekick/<lang>/templates`, embedded with `//go:embed all:templates`
and parsed once by `language.MustParseTemplates`. A template is named by its
path without the extension, so `templates/common/message.gotmpl` is included
as `"templates/common/message"`.

Which templates become output files is a naming convention:

```excerpt
file: internal/sidekick/language/walk_templates_dir.go
start: "func WalkTemplatesDir("
end: "+23"
caption: Two dots in the basename (src/lib.rs.gotmpl) make an output file; one dot (enum.gotmpl) makes a partial.
```

Languages that cannot map one template to one file, such as Swift with one
file per message, build the `[]GeneratedFile` list themselves and call
`GenerateElement` per node instead; see `internal/sidekick/swift/generate.go`.

The engine deliberately removes most of `text/template`'s power. The only
functions are `include` (render a named template, with a leading newline
and no trailing one) and `indent`; `missingkey=error` is set; and
`Templates.Validate` rejects the following at test time:

```excerpt
file: internal/sidekick/language/gotemplate.go
start: "bannedIdentifiers = map[string]bool{"
end: "+16"
caption: No comparisons, no arithmetic, no len or index. Variable mutation, break, continue and method calls with arguments are banned too.
```

Every codec package should carry a `TestValidateTemplates` that calls
`parsedTemplates.Validate()`, as `codec_sample/generate_test.go` does, so a
banned construct fails `go test` rather than a later review.

Output files must start with the license header, rendered through a partial
that reads `CopyrightYear` and `BoilerPlate` from the model annotations:

```excerpt
file: internal/sidekick/codec_sample/templates/readme/README.md.gotmpl
start: "{{- include \"templates/partials/prologue-md\" . }}"
end: "+6"
caption: The partial prologue-md emits the DO NOT EDIT marker and the Apache header; one such partial per comment syntax.
```

Formatting rules for the templates themselves, such as aligning `{{- range }}`
with the generated code's indentation, are in
`doc/styleguide/go-template-style-guide.md`.

## Registering the language in `internal/librarian`
<!-- step runs="Librarian repository" code="librarian" -->

Two switches in `internal/librarian/generate.go` are mandatory. The first is
`generateLibraries`, where each language chooses its own concurrency and
calls its `Generate` then `Format`:

```excerpt
file: internal/librarian/generate.go
start: "func generateLibraries("
end: "+16"
caption: The Dart case is the simplest one to copy; an errgroup, Generate, Format.
```

The second is the one the scaffolding skill forgets. `generate` empties the
output directory before generating, and `cleanLibraries` errors for any
language it does not know:

```excerpt
file: internal/librarian/generate.go
start: "func cleanLibraries("
end: "default:"
caption: For most languages the case is one line, checkAndClean(library.Output, library.Keep). Rust computes a wider keep list for veneers.
```

Recommended, because otherwise `librarian.yaml` must spell out everything:

| Function | File | What it gives you |
|---|---|---|
| `defaultOutput` | `internal/librarian/generate.go` | `output` derived from the name or API path instead of `default.output` verbatim |
| `deriveAPIPath` | `internal/librarian/generate.go` | `apis[0].path` derived from the library name when the mapping is not `-` to `/` |
| `install` switch | `internal/librarian/install.go` | `librarian install` provisions the language toolchain from `tools:` |
| `deriveLibraryName` and `addNewLibrary` | `internal/librarian/add.go` | `librarian add <api>` names the library and fills language defaults |
| `languageTidiers` and `languageValidators` | `internal/librarian/tidy.go` | normalization and validation during `tidy`; maps rather than switches |

```excerpt
file: internal/librarian/generate.go
start: "func deriveAPIPath("
end: "+9"
caption: Dart needs its own case because its names use underscores.
```

Release tooling (`bump.go`, `publish.go`, `docindex.go`,
`release_please.go`) has its own per-language branches and is not needed for
generation to work.

## The scaffolding skill, and where it is stale
<!-- step runs="Librarian repository" code="librarian" -->

`.agents/skills/new-sidekick/SKILL.md` is a step-by-step scaffold for the
same work. It is useful for the file list and the invariants checklist, and
its "Step 4" is the registration list:

```excerpt
file: .agents/skills/new-sidekick/SKILL.md
start: "### Step 4: Hook into Librarian Core"
end: "+20"
caption: Four registration points. The tree needs more than that.
```

Read it with these corrections in mind, all verified against the tree this
page was built from:

- It describes `.mustache` templates, a `prologue.mustache` partial and
  `{{> /templates/partials/prologue}}` includes. The engine only parses
  `.gotmpl` files, and `codec_sample`, Rust, Swift and Dart contain no
  Mustache templates. Use the `.gotmpl` form shown in the previous step.
- Its `Generate` snippet calls `libraryToModelConfig(library, library.APIs[0], sources, pc)`
  with variables that do not exist in the surrounding function and without
  defining the function. You write it yourself; the Dart version above is
  the model.
- It omits `cleanLibraries`, `defaultOutput`/`deriveAPIPath`, `install`,
  `add`, `tidy`, the `doc/config-schema.md` regeneration and, most
  importantly, CI.

## Testing and CI
<!-- step runs="Librarian repository; GitHub Actions" code="librarian" -->

Codec tests are hermetic: build a model with the fluent builders in
`internal/sidekick/api/test.go` (`api.NewTestAPI`, `NewTestMessage`,
`NewTestService`, `NewTestMethod`, `NewTestField`, ...), call `Generate`
into `t.TempDir()`, and compare files with `cmp.Diff` against inline raw
strings. There is no golden-directory framework; the expected output lives
in the `_test.go` files, split by feature as in
`internal/sidekick/swift/generate_*_test.go`.

```excerpt
file: internal/sidekick/codec_sample/generate_test.go
start: "func TestValidateTemplates(t *testing.T) {"
end: "+4"
caption: The cheapest and most valuable test in the package.
```

Tests that go through the real parser need `protoc` on `PATH` and the
fixtures under `internal/testdata`; follow the `requireProtoc(t)` pattern in
`internal/sidekick/rust/generate_test.go` so they skip cleanly where it is
missing. Run everything with:

```sh
go test -short ./internal/sidekick/<lang>/... ./internal/librarian/<lang>/...
```

CI is where new languages silently get no coverage. The generic workflow
excludes the sidekick tree and the existing per-language packages from its
coverage job, because each of those needs its own toolchain:

```excerpt
file: .github/workflows/ci.yaml
start: "go run ./tool/cmd/coverage -target=80"
end: "+1"
caption: internal/sidekick is excluded wholesale; internal/librarian/<lang> is excluded by name, so add yours to the list.
```

Each sidekick language therefore has a dedicated workflow that installs its
toolchain and runs the coverage tool over its two packages. Copy
`.github/workflows/dart.yaml`, swap the SDK setup step, and point the last
line at your packages:

```excerpt
file: .github/workflows/dart.yaml
start: "- name: Run tests and check coverage"
end: "+1"
caption: One line per language; the coverage tool enforces the threshold.
```

Rust and Swift share `.github/workflows/sidekick.yaml`, which also has an
`integration` job that checks out the Rust language repository and runs
`librarian install` and `librarian generate --all` on pushes to `main`.
That is the only end-to-end check in this repository and a good model once
your language repository exists:

```excerpt
file: .github/workflows/sidekick.yaml
start: "integration:"
end: "+24"
caption: Generate every library in a real consumer, then compile one crate.
```

## Recap: the checklist
<!-- step runs="Everywhere" code="summary" -->

| Mandatory for `generate` | Recommended for parity | Optional |
|---|---|---|
| `internal/config/language.go`: `Language<Lang>` constant | `doc/config-schema.md` regenerated | `library.go`: `isMixedLibrary`, `canDeriveAPIPath` |
| `internal/config/<lang>.go`: default and library structs | `generate.go`: `defaultOutput`, `deriveAPIPath` | `tidy.go`: tidier and validator |
| `internal/config/config.go`: `Default.<Lang>`, `Library.<Lang>` | `install.go`: `<lang>.Install` | `bump.go`, `publish.go`, `docindex.go`, `release_please.go` |
| `library.go`: `fillDefaults` + `fill<Lang>`, `resolvePreview` + `merge<Lang>` | `add.go`: `deriveLibraryName`, `addNewLibrary` | `sdk.yaml`: `release_level.<lang>`, `transports.<lang>` |
| `generate.go`: `generateLibraries` and `cleanLibraries` cases | `.github/workflows/<lang>.yaml` and the `ci.yaml` exclusion | `ModelConfig.Language` (set it for consistency; no parser branch on it was found while writing this page) |
| `internal/librarian/<lang>/`: `Generate`, `Format`, `libraryToModelConfig` | an `integration` job once a consumer repository exists | |
| `internal/sidekick/<lang>/`: codec, `annotate_*.go`, `templates/**/*.gotmpl` | | |

Three things to check before opening the pull request:

1. `librarian generate --all` in a scratch repository with a one-library
   `librarian.yaml` succeeds twice in a row (the second run exercises
   `cleanLibraries` and `keep`).
2. `go test ./...` passes, including `TestValidateTemplates` and the
   `tool/cmd/walkthrough` build, which fails if a code change moves an
   excerpt anchor used by these pages.
3. The new workflow ran on your pull request and its coverage step passed.

To change what an existing language emits rather than add one, continue
with
[Changing what sidekick generates for one language](modify-language-generation.html).
