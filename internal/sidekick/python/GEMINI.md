# Python Sidekick Guidelines for Gemini

## Overview

`internal/sidekick/python` is the native Go code generator in Librarian for
Google Cloud Python client libraries. It generates idiomatic, production-grade
Python GAPIC client code from `api.API` models using Mustache templates and
decomposed annotations, achieving parity with legacy `gapic-generator` output.

This package follows the architectural guidelines in
[`internal/sidekick/GEMINI.md`](../GEMINI.md) and the phased roadmap in
`python_migration_plan.md`.

## Architectural Invariants

### 1. 8-Node Decomposed Annotators (1:1 with Test Files)

Annotation logic is split into dedicated source and test files per AST node
type:
- `annotate_model.go` & `annotate_model_test.go` (`modelAnnotations` attached to
  `model.Codec`)
- `annotate_service.go` & `annotate_service_test.go` (`serviceAnnotations`
  attached to `service.Codec`)
- `annotate_method.go` & `annotate_method_test.go` (`methodAnnotations` attached
  to `method.Codec`)
- `annotate_message.go` & `annotate_message_test.go` (`messageAnnotations`
  attached to `message.Codec`)
- `annotate_field.go` & `annotate_field_test.go` (`fieldAnnotations` attached to
  `field.Codec`)
- `annotate_oneof.go` & `annotate_oneof_test.go` (`oneofAnnotations` attached to
  `oneof.Codec`)
- `annotate_enum.go` & `annotate_enum_test.go` (`enumAnnotations` attached to
  `enum.Codec`)
- `annotate_enum_value.go` & `annotate_enum_value_test.go`
  (`enumValueAnnotations` attached to `enumValue.Codec`)

`annotate_model.go` acts as the coordinator, annotating messages and enums
first before annotating services.

### 2. Template-First Emission

Zero in-Go Python string building or syntax construction. Never assemble Python
classes, methods, docstrings, decorators, or routing matchers in Go via
`strings.Builder` or `fmt.Sprintf`.
Mustache templates (`templates/*.mustache`) and reusable partials own all
syntax, formatting, and docstrings.
Standard Apache 2.0 license and file banners are defined in
`templates/partials/prologue.mustache` and included via `{{> prologue}}`.

### 3. Output Containment

All generated files must be contained strictly under `outdir`. Escaping `outdir`
via `..` relative paths is strictly forbidden to ensure `librarian clean` and
hermetic generation function properly.

### 4. Test Conventions

- **Always use `api.NewTest*()` builders**: Never construct raw `api.*` structs
  manually. Use the fluent constructors from `internal/sidekick/api/test.go`
  (`api.NewTestAPI`, `api.NewTestService`, `api.NewTestMethod`,
  `api.NewTestMessage`, `api.NewTestField`, `api.NewTestOneOf`,
  `api.NewTestEnum`, `api.NewTestEnumValue`).
- **Table-Driven Tests**: Use `for _, test := range []struct { name string; ...
  } { t.Run(test.name, func(t *testing.T) { ... }) }`.
- **Exact Diff Formatting**: Use `cmp.Diff(test.want, got)` formatted exactly
  as `t.Errorf("mismatch (-want +got):\n%s", diff)`.
- **Error Handling**: Use `if err != nil { t.Fatal(err) }`.
- **No Fixture Branching**: Never branch on test fixture names in production
  code.

## Formatting & Linters

Python source generated by Sidekick is formatted and linted using `ruff`:

```bash
# Format Python code
ruff format <directory>

# Lint and auto-fix Python code
ruff check --fix <directory>
```

## Go Verification Workflow

When modifying `internal/sidekick/python`:

```bash
# Format Go code
gofmt -s -w internal/sidekick/python

# Organize imports
go tool goimports -w internal/sidekick/python

# Run linter
go tool golangci-lint run ./internal/sidekick/python/...

# Run unit tests
go test -v ./internal/sidekick/python/...

# Run race detector
go test -race ./internal/sidekick/python/...
```
